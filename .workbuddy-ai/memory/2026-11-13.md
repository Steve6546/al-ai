## 2) استضافة المشروع — ماذا وجدت
### FeatherPanel (`panel.quaxly.com`) — لا يصلح
- الـMCP الرسمي داخل مستودع `MythicalLTD/FeatherPanel` تحت `mcp/`: **104 أدوات**، بنيته وشغّلته محلياً
  (غير منشور على npm، والمسار البعيد `/mcp` يرد **502**).
- الحساب (`whoami`): `_shwc` id 397، `role: user`، `permissions: []`، `webspace_limit: 0`،
  `list_servers` ⇒ **0**. وحدتا web/VDS مطفأتان.
- **إنشاء سيرفر مستحيل من الحساب:** `POST /api/user/servers/create` ⇒ `405`، و`/api/user/store*` ·
  `/api/user/billing` · `/api/user/credits` ⇒ `404`، وأدوات الـMCP لا تحتوي create/delete/suspend.
- **قاعدة البيانات MySQL فقط**، ومشروعنا PostgreSQL خالص (`pg` + `JSONB` + `ON CONFLICT`).
- النتيجة: أُبقي مربوطاً بـ`enabled: false`، والتوثيق في `docs/FEATHERPANEL-MCP.md`.

### Bot-Hosting.net — يصلح فعلاً
- `https://bot-hosting.net/api/v1` (72 نقطة) وMCP على `/api/mcp` (**72 أداة**). `initialize` و
  `tools/list` **مفتوحان بلا مفتاح** (تحقّقت: السيرفر يرد `Bot-Hosting 1.0.0`)، و`tools/call` يرد
  `-32001 Authentication required` حتى يُمرَّر `bhk_…`.
- **PostgreSQL / MySQL / MongoDB / Redis** كأنواع نشر مستقلة ⇒ **لا تعديل على طبقة البيانات**.
  Node 24 + `tsx` مدعومان. مسارات/بروكسي/سبدومين/دومين مخصص من اللوحة ⇒ **ngrok يصبح غير لازم**.
- الخطط: مجاني 256MB/نشر واحد (لا يكفي)، **Starter+ £2.59 = 2GB/4 نشرات/8GB** (المختار).
  الاستهلاك المقاس عندنا: Node ≈ 287MB + Postgres ≈ 65MB، والمعالج شبه فاضي.
- الربط الجاهز: `%USERPROFILE%\.al-ai\bot-hosting-mcp` (`mcp-remote` + `run.cmd` + `.env`) ومسجَّل في
  `opencode.jsonc` باسم `bot-hosting`. **ناقص فقط مفتاح `bhk_`** (المرسل كان مثالاً `bhk_your_key`).
- التوثيق الكامل: `docs/BOT-HOSTING-MCP.md`.

## 3) رسائل الكونسول التي أرسلها المستخدم — ليست أعطالاً
- `chrome-extension://…` و`floating-widget.js` ⇒ إضافة متصفّح، ليست من الكود.
- `gstatic.com/_/translate_http/…` ⇒ ترجمة Chrome تحقن ورقة أنماط، و`style-src 'self' 'unsafe-inline'`
  تمنعها. **القرار: لا نُرخي الـCSP** لمصلحة ميزة متصفّح؛ الحل إطفاء الترجمة التلقائية للموقع.
- `/api/health` وقتها: `healthy / connected / reachable` ⇒ لا عطل خلفي.

## 4) نشر الواجهة — `npm run deploy` + عقد شارة التحديث (تمّ)

**الطلب:** «لماذا لم تُرسل تحديثاً للموقع؟ عندنا شارة *تم التحديث* داخل الموقع؛ اجعلها أساساً ثابتاً
حتى لا تتكرر العيوب»، ثم: نفّذ وارفع كل شيء.

**التشخيص (مهم):** الخاصية **كانت موجودة وتعمل** (`components/update-banner.tsx` + `GET /api/version`)،
لكن جولة التحسين السابقة **لم تلمس `apps/dashboard/src`** ⇒ بصمة الحزمة لم تتغيّر ⇒ لا شيء لتُعلنه
الشارة. **الشيء المفقود لم يكن الشارة بل أمر نشر واحد**: كانت أربع خطوات يدوية، ونسيان الأخيرة صامت
(البناء ينجح، الصفحة القديمة تعمل، الشارة لا تظهر أبداً).

**ما أُضيف:**
- **`scripts/deploy.mjs` + `npm run deploy`:** يقرأ البصمة المخدومة → يبني → **يشغّل بوابة الأسرار على
  الحزمة الجديدة** (سطح تسريب لا يقرأه أي اختبار) → يقارن بصمة القرص بما يردّه `/api/version` الحيّ
  ويقول النتيجة صريحة. أعلام: `--no-build`، `--port`، `--url`. تحقّق: البصمة `DKGH0EHg → BdbFz0Er`.
- **`apps/dashboard/test/update-banner.test.tsx` (6 حالات):** تظهر عند اختلاف البصمة، لا تظهر عند
  تطابقها، **تبويب فُتح قبل النشر يراها من أول استطلاع** (سبب وجود الأساس)، لا تظهر عند فشل الفحص،
  ولا عند `version: null`، ووثيقة بلا وسم script لا تُطلق إنذاراً كاذباً.
- **تحقّق بالطفر (mutation):** إرجاع الأساس إلى مقارنة استطلاعين ⇒ **فشل اختباران** ⇒ الاختبار يكشف
  العيب فعلاً، لا يمرّ زوراً.
- **BOOK.md:** قسم «نشر تحديث الواجهة — `npm run deploy`» + عقد الشارة + تنبيه نشر أوامر السلاش،
  وأُضيفت `deploy.mjs` · `run-linux-stack.sh` · `port-forward.mjs` · `update-banner.tsx` لخريطة الملفات.

**آلية الشارة (لا تُنسَ):** الأساس = الحزمة التي حمّلها التبويب فعلاً من وسم `<script type="module">`،
لا أول استطلاع. تُفحص عند التحميل وكل 20s وعند `visibilitychange`/`focus`. تظهر مرة/جلسة، ولا تُعيد
التحميل بنفسها (لا يُفقد مسوّد). الواجهة تُخدَم من `dist/` على القرص ويُقرأ `/api/version` كل طلب ⇒
**تعديل الواجهة لا يحتاج إعادة تشغيل**؛ تعديل `apps/dashboard/server` يحتاجه.

**الرفع:** البعيد كان متقدّماً (4 commits: شريط السيرفرات + الاستضافة) ⇒ `git rebase origin/main`

## امتثال سياسات Discord + تصحيح مالك المنصة + تنظيف

**السياق:** طلب «مراجعة امتثال المشروع لسياسات Discord الرسمية وإصلاح أي ثغرة» من المشغّل (♪Klaus / `.shwc`).

**1) User-Agent لطلبات Discord API — ثغرة امتثال حقيقية.**
وثيقة Discord (docs.discord.com/developers/reference): «Clients using the HTTP API must provide a valid User
Agent… `User-Agent: DiscordBot ($url, $versionNumber)`… requests that do not have a valid User Agent may be
blocked and return a Cloudflare error.» أُضيف الثابت `DISCORD_USER_AGENT` في `apps/dashboard/server/discord.ts`
وطُبِّق على **كل** الطلبات الأربعة (GET، POST، oauth2/token، widget)، وكذلك `scripts/oauth-preflight.mjs`.
اختبار انحدار «every Discord call identifies itself with the documented User-Agent» في `discord-upstream.test.ts`.

**2) OWNER_ID كان على الحساب الخطأ.**
القيمة كانت `1431377358903971974` (سيرفر الحلوين، اسمه الحرفي في جدول `oauth_sessions` = **LORD**). الصحيح
`951486082690744412` (سيرفر Dark_SS، الاسم = **♪Klaus**، وهو نفسه `.shwc` = حساب FeatherPanel `_shwc` =
مالك المستودع `Steve6546`؛ وثيقة HANDOVER تشهد أنه كان `OWNER_ID` «مطابقاً» قبل 2026-11-05).
**مصدر المنحة الوحيد** `env.ownerId` في `authorization.ts` (مقارنة صارمة) — **لا حالة مالك في قاعدة البيانات**.
صُحّح في `.env` وأُعيد تشغيل اللوحة فقط (البوت لا يقرأ `OWNER_ID` — يستخدم `guild.ownerId` من Discord).
تحقّق بجلسات فحص (`dev-issue-session.mts`): `951486082690744412` → `isPlatformOwner:true`،
`1431377358903971974` → `false`. (جلسات الفحص حُذفت، وجلستا المستخدم الحقيقيتان محفوظتان.)

**3) معاينة صور التضمين كانت مكسورة بقيّة CSP.**

(`img-src 'self' data: blob: https://cdn.discordapp.com`) يحجب أي مضيف آخر ⇒ **كل رابط سليم يبدو «فاشلاً»**.
نُقلت المعاينة عبر BFF (`/api/image/from-url`) على نمط `customization.tsx`، مع debounce 500ms وهيكل تحميل.
طُبّق على الصورة الكبيرة والـthumbnail.
